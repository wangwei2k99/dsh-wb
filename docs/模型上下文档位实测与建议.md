> 实测日期：2026-10-25

**真实上限实测结果**与**推荐取值**。

## 1. 为什么曾经需要实测（2026-10-25 更新：现在有官方数据了）

`contextWindow`（上下文窗口）与 `maxTokens`（单次最大输出）曾经是插件里
**唯一没有官方数据源**的字段——早期的 `GET /v3/config` 返回 `models: null`，
只能靠 `probe_context_limit.py` 反推。

**现状：`GET /v3/config` 已经按模型下发容量字段，不需要再猜。**

| 字段 | 含义 | 2026-10-25 实测 |
| --- | --- | --- |
| `models[].maxInputTokens` | 输入窗口上限 | 36 个模型里 34 个有值，范围 96K ~ 1M |
| `models[].maxOutputTokens` | 单次输出上限 | 同上有值，范围 8,192 ~ 131,072 |
| `models[].maxAllowedSize` | 请求总预算（近似窗口） | 与 `maxInputTokens` 一致 |

实测样例：

| 模型 | maxInputTokens | maxOutputTokens |
| --- | --- | --- |
| `deepseek-v4.1-flash` | 1,000,000 | 128,000 |
| `kimi-k3.1-pro` | 1,000,000 | 32,000 |
| `glm-5.3` | 1,000,000 | 64,000 |
| `minimax-m2.7` | 200,000 | 48,000 |

插件的用法：**上限从接口取，工作值由用户定**。

- `contextWindow` 三档按上限切：`1/5`、`1/2`、上限（`1M → 200K / 500K / 1M`）。
- `maxTokens` 只列不超过 `maxOutputTokens` 的档位，并补上上限本身。
- 上游对超限的 `max_tokens` **不报错、只静默截断**，所以超限档位根本不展示。

> 历史结论（下面第 3 节的实测）仍然有效：它验证的是「服务端在多少 token 处
> 硬性截断」，与接口声明的上限互为佐证，不要删。

## 2. 实测方法

采用三段式探测（见 `probe_context_limit.py`）：

1. **标定**：用 9,000 字符英文文本测出字符/Token 比例。
2. **倍增**：从起始值成倍加大输入，直到首次失败。
3. **二分**：在「最后成功」与「首次失败」之间收敛。

**成本控制**：每次请求 `max_tokens=1`，只消耗输入 Token。

**失败判定**（三重信号）：

- HTTP 状态码 ≥ 400
- 流内业务错误（`code != 0`）
- 静默截断：服务端回报 `prompt_tokens` 低于实际发送量 90%

## 3. 实测结果

### 3.1 关键发现：服务端会直接自报上限

超限时服务端返回 `HTTP 400` + 错误码 `11115`，**明确写出上限值**：

```json
{
  "code": 11115,
  "msg": "prompt is too long: 2091927 tokens > 1048576 maximum"
}
```

因此 `deepseek-v4.1-flash` 的真实上限**不是推测，是服务端自报的确切值**。

### 3.2 deepseek-v4.1-flash

| 项目 | 结果 |
| --- | --- |
| **真实上下文上限** | **1,048,576 tokens**（= 1024K = 2^20） |
| 字符/Token 比（英文） | 4.489 |
| 等价英文容量 | 约 470 万字符 |
| 超限错误码 | `11115` |

探测过程（节选）：

```
   131,072 tokens  ->  ok     实际=   130750
   262,144 tokens  ->  ok     实际=   261495
   524,288 tokens  ->  ok     实际=   522985
 1,048,576 tokens  ->  ok     实际=  1045966
 2,097,152 tokens  ->  fail   prompt is too long: 2091927 > 1048576 maximum
 1,572,864 tokens  ->  fail   1568947 > 1048576
 1,310,720 tokens  ->  fail   1307457 > 1048576
 1,081,344 tokens  ->  fail   1078652 > 1048576
```

> ⚠️ 该轮测试累计消耗约 **1032 万输入 Token**。容量探测本身有真实成本，
> 不要在生产账号上反复跑。

## 5. 推荐配置

### 5.1 标称上限 ≠ 最佳工作档位

多家实测表明，**1M 窗口的实际有效区间远低于标称值**：

- DeepSeek V4 系列社区实测：**150K–250K token 是编码任务的最佳区间**，
  响应延迟可保持在 2 秒内、精度损失最小；超过 300K 后性能明显下降
  （[Reddit 讨论](https://www.reddit.com/r/LocalLLaMA/comments/1tfhl0q/deepseek_v4s_1m_context_window_the_breaking_point/)）
- 长上下文存在普遍的「lost in the middle」现象：关键信息位于中段时，
  模型召回率显著下降（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)）

### 5.2 建议取值

`contextWindow` 直接取接口的 `maxInputTokens`，`maxTokens` 取 32K（上限低于 32K
时取上限）。插件在设置页按这个规则分档，用户不需要手算：

| 模型 | `contextWindow`（三档） | `maxTokens` | 说明 |
| --- | --- | --- | --- |
| `deepseek-v4.1-flash` | 200K / 500K / **1M** | 32K（上限 128K） | 上限 1M，DSH 用作压缩阈值 |
| `kimi-k3.1-pro` | 200K / 500K / **1M** | 32K（即上限） | 上游输出上限就是 32K |
| `kimi-k3.1-pro-highspeed` | 200K / 500K / **1M** | 32K（即上限） | 服务端实际模型为 `kimi-k3.1-highspeed` |
| `minimax-m2.7` | 40K / 100K / **200K** | 32K（上限 48K） | 窗口较小，档位按 200K 切 |

### 5.3 为什么 `contextWindow` 填标称值、`maxTokens` 取保守值

两者语义**完全不同**，容易混淆：

- **`contextWindow`**：告诉 DSH「这个模型最多能装多少」。DSH 用它计算
  **上下文压缩触发阈值**。填**准确值**最重要——填小了会过早压缩（浪费窗口），
  填大了会不压缩、直接撞上游硬上限而报错。
- **`maxTokens`**：单次响应允许的最大输出。它与输入共享同一个 1M 预算。
  设成 128K 意味着最坏情况要挤占 128K 输入空间，且实际极少需要，
  还会拉长响应时间。`32000` 覆盖绝大多数单文件生成场景。

> **修正说明**：早期曾建议把 `contextWindow` 降到 `256000` 以求稳妥，
> 该建议基于「无官方数据」的假设。实测确认上限就是 `1048576` 后，
> 应填准确值，不必过度保守。

## 6. 其他实测所得的行为特征

### 6.1 仅支持流式

非流式请求直接被拒：

```json
{ "code": 11101, "msg": "Non-stream chat request is currently not supported" }
```

插件始终使用 `stream: true`，符合要求。第三方直连调试时注意此点。

### 6.2 服务端会改写模型名

| 请求的模型 ID | 服务端回显 |
| --- | --- |
| `deepseek-v4.1-flash` | `deepseek-v4.1-flash` ✅ |
| `kimi-k3.1-pro` | `kimi-k3.1-pro` ✅ |
| `kimi-k3.1-pro-highspeed` | **`kimi-k3.1-highspeed`** ⚠️ |

`-highspeed` 是别名，后端实际模型 ID 少了 `pro`。不影响调用，但排查日志时需留意。

### 6.3 思考档位

Kimi K3.1 Pro 系列**仅支持思考模式**，传 `off` / `none` 会被拒（HTTP 400）。
官方档位映射：

| 传入 | 实际 |
| --- | --- |
| `ultra` / `max` / `xhigh` | `max` |
| `high` / `medium` | `high` |
| `low` / `minimum` / `light` | `low` |
| `off` / `none` / `disabled` | K3.1 Pro 拒绝；其他退回 K2.8 无思考版 |

本插件 `THINKING_LEVELS = ["off", ...EFFORTS]`，对 K3.1 Pro 需避免选 `off`。

### 6.4 出站身份（令牌登录 vs API Key）

插件按认证方式使用两套出站身份，定义在 `workbuddy-auth.js`。WorkBuddy 身份
**完整对齐** [workbuddy2api-hub](https://github.com/ardeyouxipianyi/workbuddy2api-hub)
`wb_identity.py` 的 `PRODUCT_DESKTOP` 分支。

**静态头**

| 头 | CLI 身份（API Key） | WorkBuddy 身份（令牌登录） |
| --- | --- | --- |
| `User-Agent` | `CLI/2.171.0 CodeBuddy/2.171.0` | `WorkBuddy/5.8.3 WorkBuddy/5.8.3 CLI/2.161.0` |
| `X-IDE-Type` | `CLI` | `WorkBuddy` |
| `X-IDE-Name` | `CodeBuddy` | `WorkBuddy` |
| `X-IDE-Version` | `2.171.0` | `5.8.3` |
| `X-Agent-Intent` | — | `craft` |
| `X-Agent-Purpose` | — | `conversation` |
| `X-Agent-Type` | — | `main` |
| `X-Product` | `SaaS` | `SaaS` |
| `X-Private-Data` | — | `true` |
| `X-Domain` | — | `copilot.tencent.com` |
| `X-User-Id` | — | 账号 userId，缺省 `anonymous` |

**会话头族**（缺失会触发上游渠道校验 `400 / conversation id missing`）

| 头 | 形态 | 说明 |
| --- | --- | --- |
| `X-Conversation-ID` | 带连字符 UUID | 按「账号 + 会话」稳定派生，多轮复用 |
| `X-Conversation-Request-ID` | 32hex | 一轮 user send 内复用 |
| `X-Root-Request-ID` | 32hex | 与上一项同值 |
| `X-Conversation-Message-ID` | 32hex | 每请求新生成 |
| `X-Request-ID` | 32hex | 与上一项同值 |

**链路头族**

| 头 | 形态 |
| --- | --- |
| `X-Trace-ID` | 32hex，与 `X-B3-TraceId` 同值 |
| `traceparent` | `00-<32hex>-<16hex>-01` |
| `b3` | `<32hex>-<16hex>-1`（桌面端三段，无父 span） |
| `X-B3-TraceId` / `X-B3-SpanId` / `X-B3-Sampled` | `32hex` / `16hex` / `1` |

系统提示词中的自称同步切换（`You are WorkBuddy / CodeBuddy`）。

**实测**：两套身份对 `POST /v2/chat/completions` 均返回 `200`；
WorkBuddy 身份的 SSE 流会额外出现 `: heartbeat` 事件，属桌面端链路特征。

**未实现项**（参考实现中桌面端默认关闭，故未发送）：

- `x-stainless-*` 系列指纹头 —— 仅在 `WB_DESKTOP_CHAT_COMPAT=1` 时桌面端才发。
- `X-Enterprise-Id` / `X-Tenant-Id` —— 企业账号才有；本插件已在登录会话
  存在 `enterpriseId` 时通过 `context.headers` 发送。
- `X-API-Key` —— 只在 API Key 模式发送（同时发 `Authorization`），令牌模式不发。

### 6.5 登录平台决定跳转域名

`POST /v2/plugin/auth/state?platform=<值>` 返回的 `authUrl` 由平台参数决定：

| `platform` | 返回的 `authUrl` |
| --- | --- |
| `WorkBuddy` | `https://www.workbuddy.cn/login?...` |
| `workbuddy` | `https://www.workbuddy.cn/login?...` |
| `CLI` | `https://copilot.tencent.com/login?...` |
| `Desktop` | `https://copilot.tencent.com/login?...` |
| `VSCode` | `https://copilot.tencent.com/login?...` |

**本插件使用 `WorkBuddy`**，令牌登录会落在 WorkBuddy 官网而不是 CodeBuddy 控制台。
实测该 state 的后续 `GET /auth/token?state=` 返回 `code: 11217 / login ing...`，
属正常等待态（轮询逻辑只在 `code === 0` 时返回，401/403 才视为失败）。

> 两个产品同属腾讯、共享底层，但**登录入口与品牌是两个域名**：
> `www.workbuddy.cn`（办公场景）与 `www.codebuddy.cn`（编程场景）。

### 6.6 登录请求头（对齐参考实现）

参考 `workbuddy2api-hub` 的 `start_login` / `poll_login`，登录链路的三个接口
（`auth/state`、`auth/token`、`login/account`）需要浏览器侧头族：

| 头 | 值 |
| --- | --- |
| `User-Agent` | `WorkBuddy/5.8.3`（两段式 `billing_ua`） |
| `Origin` | `https://www.workbuddy.cn` |
| `Referer` | `https://www.workbuddy.cn/` |
| `X-Requested-With` | `XMLHttpRequest` |
| `Accept` | `application/json, text/plain, */*` |

注意与**会话请求**的 UA 不同：会话用三段式
`WorkBuddy/5.8.3 WorkBuddy/5.8.3 CLI/2.161.0`（`chat_ua`），
登录/计费类接口用两段式 `WorkBuddy/5.8.3`（`billing_ua`）。

**实测矩阵**（`Origin` 与 `platform` 交叉）：

| Origin | platform | 结果 | authUrl 域名 |
| --- | --- | --- | --- |
| codebuddy.cn | WorkBuddy | 200 | `www.workbuddy.cn` |
| workbuddy.cn | WorkBuddy | 200 | `www.workbuddy.cn` |
| workbuddy.cn | CLI | 200 | `copilot.tencent.com` |
| codebuddy.cn | CLI | 200 | `copilot.tencent.com` |

结论：**只有 `platform` 决定登录域名，`Origin` 不影响**。四种组合均返回 200。
本插件令 `Origin` 与登录页域名保持一致（`workbuddy.cn`），语义更自洽。

`11217` 是参考实现里的 `LOGIN_PENDING` 常量，与本插件实测一致。

### 6.6 超窗请求不会报错，只会「回 1 个 token」

把「上下文窗口」调小到低于会话已有体积之后（例如 1M → 200K），每次请求都变成：

| 观察项 | 实测值 |
| --- | --- |
| `finish_reason` | `length` |
| `usage.output_tokens` | `1`（正文可能只有一两个字） |
| HTTP 状态 | `200`，没有任何业务错误码 |
| DSH 界面 | 「已达到输出 token 上限 回答被截断」+「继续」按钮 |

同一份会话里 `usage.input_tokens` 会明显大于 `contextWindow`（实测 757K / 596K /
468K … 对 200K 窗口），说明输入本身已经塞满甚至超过窗口，上游把剩余预算压到 1 个
token 后正常结束。

**这解释了两种误判：**

1. 用户以为是「输出被截断」，去把「最大输出 Token」从 32K 调到 128K —— 无效，
   因为瓶颈是输入。
2. DSH 把 `length` 显示成「输出 token 上限」，不会触发自己的自动压缩；压缩请求
   （summarize）同样带着超窗输入，于是也被截断，报
   `summarization truncated at the token cap (incomplete checkpoint)`，会话卡死。

**插件的处置**（`index.js` 的 `boundContextBudget` / `silentContextOverflow`）：

- 发请求前估算输入体积，放不下完整 `maxTokens` 时按剩余空间收敛。
- 输入已塞满窗口 → 抛 `CONTEXT_WINDOW_EXCEEDED`（错误文本固定包含
  `context_length_exceeded`，DSH 按英文措辞识别溢出）。
- 上游仍返回「1 个 token + `length`」→ 同样改判为溢出。

DSH 的 `agent/request-error` 监听器收到该码后会做一次头部裁剪并重试，会话即可恢复。

## 7. 复现方式

```powershell
# 全量探测（成本较高）
python probe_context_limit.py --model deepseek-v4.1-flash --start 131072 --cap 2097152

# 低成本验证（仅确认已知上限以内可用）
python probe_context_limit.py --model deepseek-v4.1-flash --start 4096 --cap 65536
```

脚本自动从 `~/.dsh/.credentials.yaml` 读取当前 activeId 对应的 Key，
也可通过 `--key` 或环境变量 `WORKBUDDY_API_KEY` 指定。

## 8. 边界与免责

1. 这是**非公开、非承诺稳定**的接口，路径与字段可能随官方客户端更新而变。
2. 上限受**账号档位**影响，不同会员等级、不同 Key 可能得到不同结果。
3. 本文的 `1048576` 是当前 Key、当前档位下的实测值，非永久保证。
4. 容量探测会消耗真实额度，请勿在共享或生产账号上反复执行。

## 9. 第三方项目的实测结论与风控警告

本节汇总 GitHub 上同类项目的公开实测记录，用于校验本插件的实现假设。
**这些是他人环境下的观测，不构成对本插件行为的保证。**

### 9.1 已确认与本文一致的结论

| 结论 | 来源 | 与本插件的关系 |
| --- | --- | --- |
| `POST /v2/chat/completions` 必须 `stream: true`，否则返回 `code 11101` | `cainiao1992/dsh-codebuddy-auth` 实测 | 本插件始终流式，符合 |
| 聊天端点**不校验 User-Agent**，任意 UA 可用 | 同上 | 身份头的作用在渠道校验层面，非 UA 白名单 |
| `GET /v3/config` 需 craft/VSCode 身份才下发思考元数据 | 同上 | 本插件令牌模式已带 `X-Agent-Intent: craft` |
| 静态 Key 需同时发 `Authorization` 与 `X-API-Key` | `workbuddy2api-hub` | 本插件已双发 |

### 9.1.1 会话头族的必要性：A/B 实测

`decolua/9router` 的 [issue #5005](https://github.com/decolua/9router/issues/5005) 提供了逐头对比的实测数据
（国际站网关自 2026-10-15 起启用渠道校验）：

| 发送的头 | 结果 |
| --- | --- |
| 全部不发 | `HTTP 400` code `11128` |
| 只发 `X-Conversation-ID` | `HTTP 400` code `11128` |
| 只发 `X-Conversation-Request-ID` + `X-Conversation-Message-ID` | `HTTP 400` code `11128` |
| **三个全发** | **`HTTP 200`，SSE 正常流式** |

结论：**三件套缺一不可**，任意两个仍返回 400。

本插件实测（国内站 `copilot.tencent.com`）：

```
x-conversation-id           = f82ebe32-edb7-48dd-a423-32b9d20ca9f0
x-conversation-request-id   = a07522ac3d54426f8902ffb695eb24de
x-conversation-message-id   = ecf500f17a0a45958e6d19ce22610635
→ HTTP 200 + ": heartbeat" + 正常 chunk
```

### 9.1.2 `11128` 是重载错误码：必须按 message 分支

同一 issue 明确指出：

> **`11128` is overloaded.** Once the header family is present, the *same code*
> comes back as `"first message is not system prompt"`, a body-shape issue,
> not channel verification. **Branch on the message text, not the code alone.**

| `msg` 内容 | 真实原因 | 处置 |
| --- | --- | --- |
| `conversation id missing` / `request illegal` | 渠道校验：缺会话头族 | 补 `X-Conversation-*` 三件套 |
| `first message is not system prompt` | 请求体形状问题 | 首条消息须为 system |
| 其他未知文本 | 无法判定 | **不猜测**，如实提示查看业务消息 |

本插件已按此实现（`index.js` 的 `normalizeWorkBuddyError`），并按 msg 分支出三种提示。

> 早期实现只按 code 判断、一律提示"渠道校验未通过"，属于误诊——
> 已修正。对应测试（`test.js`）覆盖了两种 msg 分支。

### 9.2 需要警惕的风控信号

**账号级限制（code 11140）**

`dingminhua/dsh-connect-workbuddy`（583★）记录了：

> 上游风控升级到「按提示词中段做精确子串匹配」，靠插零宽字符躲避已是军备竞赛，
> 而且不再免费：issue #98 已出现**账号级**限制（`code 11140`，「账号存在异常行为，已被限制使用」）。

`9router` issue #5005 的评论者给出了同样结论，并强调它**不是客户端问题**：

> The next blocker is **account-level**. On accounts the header fix gets past the gate,
> the gateway then answers `HTTP 403 code 11140 "Your account has been restricted due to
> unusual activity"`. **Nothing client-side fixes that**; it needs a non-restricted account.
> Calling this out so 11140 isn't misread as "the fix didn't work".

**关键区分**（同一项目）：

| 错误码 | 含义 | 换号是否有用 |
| --- | --- | --- |
| `11140` 账号被限制 | 上游点名**这个账号** | ✅ 换号可绕过 |
| 渠道校验失败 | 说的是**这个请求** | ❌ 换号只白烧额度 |
| `11128` 请求被拒 | 内容/身份校验 | 取决于具体原因 |

**`11140` 是服务端策略拒绝，重新登录无法解决** —— 这一点对本插件尤为重要：
遇到 `11140` 不应提示用户"重新登录"，而应如实说明是账号/内容侧限制。

**另一个项目的结论更直接**

`functy23/dsh-workbuddy-connect-functy` 已**归档**，理由写得很明确：

> 上游风控持续加强、UA/请求头格式频繁变动，适配已难以为继。

### 9.3 对本插件的含义

综合以上，本插件在身份层面的**已知边界**：

1. **身份头能做到"像"官方客户端，但做不到"是"官方客户端。**
   缺少的核心要素是 `X-Device-Token`（需本机 QIMEI/TuringShield 原生 SDK 生成，
   第三方无法伪造）。参考实现对此的选择是明确发送
   `X-Device-Token-Error: sdk_not_initialized` 而非伪造。

2. **TLS 指纹不在 HTTP 头层面可伪装范围。** Python/Node 的 TLS 栈与 Electron
   客户端的握手指纹不同，这是可被识别的维度。

3. **行为模式（请求频率、时序）同样参与判定。**
   本插件不做请求节流或随机化——它作为 DSH 的模型提供方，请求频率由用户使用决定。

4. **结论：本插件无法保证账号不受限制。** 上述第三方项目均在不同程度上
   投入了反风控工程（限速、随机延迟、UA 轮换），本插件**没有**做这些，
   因为它定位是"在 DSH 里使用你自己的 WorkBuddy 账号"，而非对外提供代理服务。

### 9.4 一个关于思考内容计费的实测

`dingminhua` 项目的 issue #59 / #75 记录了一个深层机制，与本插件的
`reasoningEffort` 配置相关：

> 同一份历史在两个区域（国内/国际）的计费口径不同。pi-ai 给每条 assistant
> 消息算一次 `isSameModel`（判据是 provider **且** api **且** model id 三者全等）；
> 不等的消息，其 thinking 会被**降级成普通正文**，而正文是网关会数的，
> thinking 走另一个字段（`reasoning_content`）。

后果：**跨 provider 或跨模型切换会让 token 计数跳变 ±30%~94%**，
进而可能触发 `code 11115 prompt is too long`。

本插件只有一个 provider 路由（`workbuddy-cn`），不存在跨区域切换问题；
但**在同一会话内切换模型**仍会触发该降级，这是 DSH/pi-ai 层的既有行为，
不是本插件引入的。
